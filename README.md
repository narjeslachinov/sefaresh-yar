# سفارش‌یار

سفارش زنده سر میز و نمایش آن در آشپزخانه برای کافه‌رستوران‌های ایران.

**نشانی محیط زنده:** https://95-38-187-46.sslip.io
**ورود:** ایمیل‌های دمو پایین‌تر آمده‌اند. رمز عمداً در این مخزن نیست و در پیام تحویل جدا داده شده است.

## وضعیت صادقانه

**چه چیزی کار می‌کند:** ورود با سه نقش (گارسون، آشپزخانه، مدیر)؛ سفارش‌گیری سر میز؛ صف آشپزخانه با به‌روزرسانی زنده؛ بستن میز و بستن اجباری توسط مدیر؛ مدیریت حداقلی منو؛ ورود منو از متن (با قواعد ساده، و با AI در صورت تنظیم)؛ جداسازی کامل داده بین رستوران‌ها در سطح دیتابیس؛ دو رستوران نمایشی با تاریخچهٔ ۱۴ روزه؛ استقرار روی HTTPS (از بیرون بررسی شده: گواهی پذیرفته می‌شود و درخواست بدون نشست به `/login` هدایت می‌شود).

**چه چیزی ساخته نشده یا کار نمی‌کند:**
- **چند شعبه ندارد** (طرح در SCOPE بند ۷ و DECISIONS D13).
- پرداخت، تخفیف، مالیات، گزارش و صندوقدار ندارد.
- مدیریت کارکنان و میزها از داخل برنامه نیست؛ حساب‌ها را توسعه‌دهنده می‌سازد (`npm run user:create`).
- تغییر یا فراموشی رمز نیست.
- بدون اینترنت کار نمی‌کند.
- **بار هرگز اندازه‌گیری نشده است.** تعداد اتصال‌های زنده سقف ندارد و Pool دیتابیس ۱۰ اتصال است (DECISIONS R3).
- تست‌ها فقط روی `next dev` اجرا می‌شوند و رابط کاربری تست مرورگر ندارد.
- قابلیت AI فقط با ارائه‌دهندهٔ آزمایشی (mock) تست شده و **روی سرور زنده خاموش است**.
- راه‌اندازی از صفر **یک دستور نیست**؛ چند دستور است (پایین‌تر) (DECISIONS R7).
- **پشتیبان‌گیری و بازسازی روزانهٔ دمو روی سرور زنده خودکار نیست.** اسکریپت‌ها و فایل cron در `deploy/` هستند ولی نصب نشده‌اند؛ باید دستی اجرا شوند (بخش انتشار). تا آن زمان هیچ پشتیبانی گرفته نمی‌شود.
- هدرهای امنیتی (HSTS، `X-Content-Type-Options`، `X-Frame-Options`) نه در برنامه و نه در Caddy تنظیم نشده‌اند.
- پاسخ‌ها هدر `x-request-id` ندارند و درخواست‌های موفق لاگ نمی‌شوند. عیب‌یابی فقط از روی خطاها (با `requestId` در بدنهٔ خطا) و جدول `order_events` ممکن است.

فهرست کامل محدودیت‌ها در [HANDOVER.md](./HANDOVER.md) §۳ و تصمیم‌هایی که اشتباه می‌دانم در [DECISIONS.md](./DECISIONS.md) بخش «بازنگری».


## پیش‌نیازها

- Node.js 20.6 یا بالاتر (برای `--env-file`؛ در `package.json` ثبت نشده است)
- PostgreSQL 16، به یکی از دو روش:
  - **Docker:** `npm run db:up` (فایل `docker-compose.yml`، دیتابیس `sarfaresh` را می‌سازد)
  - **نصب مستقیم:** PostgreSQL را نصب کنید و دیتابیس `sarfaresh` را بسازید: `CREATE DATABASE sarfaresh;`

## راه‌اندازی محلی

```bash
cp .env.example .env.local      # در ویندوز: copy .env.example .env.local
npm install
npm run db:up                   # فقط اگر از Docker استفاده می‌کنید
npm run db:migrate              # ساخت نقش برنامه، جدول‌ها و سیاست‌های RLS
npm run seed:demo               # دادهٔ دمو
npm run dev                     # http://localhost:3000
```

در `.env.local` مقدار `SESSION_SECRET` را با یک رشتهٔ تصادفی حداقل ۳۲ نویسه‌ای عوض کنید. اگر PostgreSQL را مستقیم نصب کرده‌اید، رمز واقعی کاربر `postgres` را در `DATABASE_URL_ADMIN` بگذارید.

بررسی سلامت: `http://localhost:3000/api/health` باید `{"status":"ok"}` برگرداند. این نقطه فقط می‌گوید فرایند بالاست؛ اتصال دیتابیس را بررسی نمی‌کند.

## حساب‌های دمو

رمز از متغیر `DEMO_PASSWORD` می‌آید. اگر تنظیم نشده باشد، مقدار پیش‌فرض محلی در `scripts/seed-demo.mjs` است. **روی سرور زنده رمز متفاوت است و در این مخزن نیست.**

| رستوران | نقش | ایمیل |
|---|---|---|
| کافه‌رستوران نیلوفر | مدیر | manager@niloofar.test |
| | گارسون | waiter@niloofar.test، waiter2@niloofar.test |
| | آشپزخانه | kitchen@niloofar.test |
| کافه باغ | مدیر | manager@bagh.test |
| | گارسون | waiter@bagh.test |
| | آشپزخانه | kitchen@bagh.test |

- منوها واقع‌گرایانه‌اند و ۱۴ روز تاریخچهٔ سفارش دارند (پنجشنبه و جمعه شلوغ‌تر). قیمت‌ها تقریبی‌اند (DECISIONS D39).
- چند سفارش باز و آیتم‌های در صف آشپزخانه در **لحظهٔ Seed** ساخته می‌شوند تا صفحه‌ها خالی نباشند (D40). چون روی سرور بازسازی خودکار نیست، با گذشت روزها زمان‌ها («۴۸ دقیقه پیش») کهنه می‌شوند؛ برای تازه‌شدن، Seed را دستی اجرا کنید (بخش انتشار).
- اجرای دوبارهٔ Seed فقط همین دو رستوران را بازسازی می‌کند و تغییرهای شما روی آن‌ها را پاک می‌کند.

## معماری

- **Next.js (App Router) + TypeScript:** رابط راست‌به‌چپ و API در یک پروژه (D1).
- **PostgreSQL 16:** همهٔ دادهٔ هر رستوران با `restaurant_id` علامت‌گذاری شده است.
- **جداسازی رستوران‌ها در دو لایه** (D4 تا D6):
  1. Row Level Security: برنامه با نقش `sarfaresh_app` وصل می‌شود که Superuser نیست، `BYPASSRLS` ندارد و `DELETE` ندارد.
  2. کلید خارجی ترکیبی `(id, restaurant_id)`: هیچ رکوردی نمی‌تواند به رکورد رستوران دیگر اشاره کند.
- **`withTenant`** (`src/server/db.ts`): هر پرس‌وجو درون تراکنشی اجرا می‌شود که رستوران فعلی را با `set_config` تنظیم می‌کند. اگر تنظیم نشود، هیچ ردیفی دیده نمی‌شود.
- **هم‌زمانی** (D7، D8، D20 تا D24، D31): آیتم‌های سفارش ردیف جدا هستند؛ یک سفارش باز برای هر میز با ایندکس یکتا؛ تغییر وضعیت با مقایسه و تعویض اتمیک (`from` و `to`)؛ لغو و بستن میز idempotent هستند.
- **Idempotency** (D21): هر ضربهٔ افزودن یک `requestId` دارد؛ تکرار همان نتیجه را می‌دهد و استفادهٔ مجدد با محتوای دیگر ۴۰۹ می‌شود.
- **قیمت از سرور** (D22): قیمت و نام آیتم هنگام ثبت از منو خوانده و روی آیتم ذخیره می‌شود؛ کلاینت قیمت نمی‌فرستد.
- **به‌روزرسانی زنده** (D27 تا D30، D34، D56): جریان SSE از جدول `order_events` با Cursor؛ پیام فقط شناسه می‌برد و کلاینت دوباره می‌خواند؛ هر تب یک اتصال دارد.
- **احراز هویت** (D12، D15 تا D19): کوکی HttpOnly امضاشده؛ نقش و فعال بودن عضویت در هر درخواست از دیتابیس خوانده می‌شود؛ هش رمز با scrypt؛ بررسی Origin؛ قفل ورود بعد از ۱۰ تلاش ناموفق (در حافظهٔ سرور).
- **نقش‌ها** (P2، D32): گارسون، آشپزخانه، مدیر. مجوزها در سرور اعمال می‌شوند، نه فقط با پنهان‌کردن دکمه‌ها.
- **اعتبارسنجی** (D22، D25): Zod با `.strict()` در مرز API؛ خطاها به کد پایدار تبدیل می‌شوند؛ خطای دیتابیس جزئیات را فاش نمی‌کند.
- **لاگ ساخت‌یافته:** Pino با حذف کوکی، رمز و توکن از لاگ. **فقط خطاها و رویدادهای مهم لاگ می‌شوند** (خطای ۵۰۰، خطای دیتابیس، ورود ناموفق و قفل‌شدن، رد شدن RLS)؛ درخواست‌های موفق لاگ نمی‌شوند. پاسخ خطای ۵۰۰ و خطای دیتابیس یک `requestId` در بدنه دارد که همان در لاگ هم هست، پس از روی پیام کاربر می‌شود خط لاگ را پیدا کرد. هدر `x-request-id` و لاگ دسترسی برای هر درخواست وجود ندارد؛ برای یافتن «چه کسی چه کرد» باید از جدول `order_events` در دیتابیس استفاده کرد.

## متغیرهای محیطی

| نام | کاربرد |
|---|---|
| `DATABASE_URL` | اتصال برنامه (نقش محدود) |
| `DATABASE_URL_ADMIN` | فقط برای Migration و Seed؛ هرگز در برنامهٔ در حال اجرا استفاده نمی‌شود |
| `APP_DB_PASSWORD` | رمز نقش برنامه هنگام ساخت آن |
| `SESSION_SECRET` | کلید امضای نشست (حداقل ۳۲ نویسه) |
| `LOG_LEVEL` | `debug`، `info`، `warn`، `error` |
| `DEMO_PASSWORD` | رمز حساب‌های دمو هنگام Seed |
| `AI_PROVIDER` | `anthropic`، `openai` (هر سرویس سازگار) یا خالی برای خاموش. `mock` فقط برای تست و در production پذیرفته نمی‌شود |
| `AI_API_KEY`، `AI_MODEL` | الزامی وقتی ارائه‌دهنده انتخاب شده. نام مدل را از مستندات سرویس بردارید |
| `AI_BASE_URL` | اختیاری، برای سرویس‌های سازگار |
| `AI_TIMEOUT_MS` | پیش‌فرض ۲۰۰۰۰ |

**هیچ کلید یا رمز واقعی در مخزن نیست.** فقط `.env.example` ردیابی می‌شود و `.env*` دیگر در `.gitignore` است. تنها رمزهای ثابت داخل مخزن مال اسکریپت‌های smoke محلی (`Test-12345`) و پیش‌فرض Seed محلی (`Demo-1234!`) هستند.

`SESSION_SECRET` فقط از نظر طول (حداقل ۳۲ نویسه) بررسی می‌شود. برنامه مقدار نمونهٔ `.env.example` را در production رد نمی‌کند؛ حتماً آن را عوض کنید.

## قابلیت هوش مصنوعی: ورود منو از متن

مدیر متن منو را می‌چسباند، پیش‌نویس را می‌بیند و ویرایش می‌کند، و بعد تأیید می‌کند. **چیزی بدون تأیید مدیر ذخیره نمی‌شود.**

- **قواعد ساده اول:** متن مرتب (`نام - قیمت`) بدون AI خوانده می‌شود. AI فقط برای متن نامرتب یا با دکمهٔ تحلیل با هوش مصنوعی صدا زده می‌شود (D47).
- **خرابی بی‌ضرر:** اگر AI جواب ندهد، پاسخ نامعتبر بدهد یا سقف مصرف تمام شود، نتیجهٔ قواعد ساده نشان داده می‌شود. ثبت سفارش هیچ‌وقت به AI وابسته نیست (D50).
- **داده‌ای که می‌رود:** فقط متن منو. نه سفارش، نه مشتری، نه نام کارکنان.
- **امنیت:** متن منو داده‌ٔ غیرقابل‌اعتماد است؛ مدل ابزار ندارد؛ خروجی با Zod اعتبارسنجی می‌شود (D49).
- **هزینه:** ۱۰ درخواست در ساعت و ۳۰ در روز برای هر رستوران؛ توکن و تأخیر هر درخواست در جدول `ai_requests` ثبت می‌شود (D51).
- **ابهام قیمت:** قیمتی که حدس زده یا مشکوک است (مثلاً «۱۸۵») پرچم می‌خورد (D52).
- **وضعیت:** روی سرور زنده `AI_PROVIDER` تنظیم نشده و AI خاموش است (D64). با سرویس واقعی هرگز آزمایش نشده؛ فقط با ارائه‌دهندهٔ آزمایشی.

آزمودن با سرویس واقعی (فقط روی سروری که به سرویس دسترسی دارد): `npm run smoke:ai`. نمونهٔ متن نامرتب: `scripts/smoke-ai.mjs`.

## آزمون‌ها

```bash
npm test
```

قبل از اجرا `npm run dev` را خاموش کنید. تست‌ها یک دیتابیس تازه به نام `sarfaresh_test` می‌سازند، Migration واقعی را اجرا می‌کنند و سرور را روی پورت ۳۱۰۰ بالا می‌آورند. به دیتابیس توسعه و دادهٔ دمو دست نمی‌زنند.

| فایل | چه چیزی را ثابت می‌کند |
|---|---|
| `db-isolation` | RLS و کلیدهای خارجی ترکیبی با نقش محدود، حتی بدون کد برنامه |
| `api-workflow` | **یک سرویس کامل میز** از باز شدن تا بسته شدن، همراه با جریان زنده |
| `api-security` | نقش‌ها، رستوران دیگر، توکن جعلی، ورودی بد، Origin، قفل ورود |
| `api-concurrency` | درخواست تکراری، افزودن‌های هم‌زمان، رقابت لغو و شروع، رقابت بستن و افزودن، کامل بودن فید رویداد |
| `api-stream` | بازیابی بعد از قطع، جداسازی رستوران‌ها، بسته شدن جریان پس از لغو دسترسی |
| `api-menu-live` | رسیدن تغییر منو به گارسون بدون Refresh؛ هر تغییر یک‌بار؛ هرگز به رستوران دیگر |
| `api-menu-ai` | تغییر قیمت و «تمام شد»، ورود منو (قواعد ساده، AI، خرابی و بازگشت، تزریق دستور، سقف ۱۰ در ساعت)، یکتایی نام‌ها، بستن اجباری میز |
| `menu-text` | خواندن متن منو با قواعد ساده |

**تست نمی‌شود:** رابط کاربری (بدون تست مرورگر)، بار و کارایی، قطع و وصل واقعی شبکه، رفتار SSE پشت پروکسی واقعی، محدودیت ورود با چند نمونه، سرویس واقعی AI، کتابخانه‌های ثالث، بیلد تولید. دلیل هر کدام در [DECISIONS.md](./DECISIONS.md) D45 آمده است.

## بررسی دستی جداسازی رستوران‌ها

علاوه بر تست خودکار `db-isolation`، در `psql` با کاربر مدیر دو رستوران بسازید و با نقش برنامه امتحان کنید:

```sql
SET ROLE sarfaresh_app;
SELECT count(*) FROM restaurants;                    -- 0: بدون رستوران تنظیم‌شده چیزی دیده نمی‌شود
BEGIN;
SELECT set_config('app.restaurant_id', '<id-a>', true);
SELECT slug FROM restaurants;                        -- فقط a
INSERT INTO dining_tables (restaurant_id, label) VALUES ('<id-b>', '1');  -- خطای RLS
ROLLBACK;
```

**نشانی:** https://95-38-187-46.sslip.io
**سلامت:** https://95-38-187-46.sslip.io/api/health

یک ماشین Ubuntu (DECISIONS D57 تا D63):

- Node.js و Next.js تحت systemd (`deploy/sarfaresh.service`)، گوش‌دادن روی `127.0.0.1:3000`
- PostgreSQL محلی با نقش محدود برای برنامه
- Caddy برای Reverse Proxy و HTTPS خودکار (`deploy/Caddyfile`)، بدون هدرهای امنیتی اضافه
- تنظیمات محیطی جدا: `/etc/sarfaresh/app.env` برای برنامه و `/etc/sarfaresh/admin.env` برای Migration و Seed
- UFW و SSH مبتنی بر کلید

**لاگ برنامه:** `journalctl -u sarfaresh -o cat`
**وضعیت سرویس‌ها:** `systemctl is-active sarfaresh caddy`

### به‌روزرسانی نسخهٔ مستقر

ابتدا `npm test` و `npm run build` را محلی اجرا کنید. سپس آرشیو tar را به سرور بفرستید و `deploy/update.sh` را اجرا کنید؛ این اسکریپت فایل‌ها را باز می‌کند، `npm ci` و بیلد را اجرا می‌کند، Migration را با `admin.env` می‌زند، سرویس را راه‌اندازی مجدد می‌کند و سلامت را می‌سنجد.

### پشتیبان و بازسازی دمو (دستی)

اسکریپت‌ها و فایل cron در `deploy/` هستند، ولی **روی سرور نصب نشده‌اند**. تا نصب نشوند، این دو کار خودکار انجام نمی‌شود:

```bash
# پشتیبان (فایل در /var/backups/sarfaresh ذخیره می‌شود، روی همان سرور)
```
